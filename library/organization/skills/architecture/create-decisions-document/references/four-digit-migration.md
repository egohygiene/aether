# Four-digit ADR migration

The selected Hygiene policy owns this convention. This procedure applies an explicitly authorized padding-only upgrade; it supplies no architectural acceptance.

1. Verify the repository default-branch revision, scoped instructions, selected policy, record/index ownership and open overlapping PRs. Inventory canonical files and inline decision headings; distinguish current sources from immutable evidence and imported material.
2. Group IDs by their numeric value across all widths and prefixes. Stop on collisions or uncertain canonical identity. Keep each logical number and established legacy prefix; new canonical records use `ADR-NNNN`.
3. Record authorization and one row per changed record: old/new ID, old/new path or inline anchor, source revision and migration date. Retain the prior pin and path in Git.
4. Rename and update the front matter, heading, index row, lineage, current local/cross-repository links and declarations together. Preserve rationale, historical dates, decision status, approval and implementation evidence. Do not rewrite old Git messages, immutable blob links, dated receipts or recorded rollback bytes.
5. Adopt the same reviewed policy tuple in the consumer reference, native validator configuration, shared runtime and authoring/scaffold selections. Reconcile generated files through their owning materializer and preserve unrelated instruction blocks.
6. Validate the complete corpus, index uniqueness, reference/lineage resolution and exact source/tool pins. Compare migrated source to the prior revision with only mapped IDs/references reversed; account explicitly for any additional dated note. Preserve unknown authority and failed publication gates.
7. Review the bounded diff and merge under the maintainer's authorization. Refresh continuity and the central tracker with exact PRs and remaining adoption gaps. A passing numbering check does not complete historical backfill, ratification or deployment.

Old commit trailers remain historical text. The selected validator may resolve a three-digit historical reference to an existing padded target; never create a fictional target to make history pass. A URL compatibility layer is a separate product decision when it is needed.
